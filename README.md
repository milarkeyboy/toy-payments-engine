# Toy Payments Engine

A small engine for processing payments to/from client accounts.

## DISCLAIMER

AI was used in writing and testing of this code. All code generated by AI agents
has been reviewed with human eyes. Please contact the maintainer should you have
any concerns.

## Usage

### Build

```bash
cargo build
```

### Run

```bash
cargo run -- <path to CSV file>
```

### Audit

If [cargo audit](https://crates.io/crates/cargo-audit) is installed:

```bash
cargo audit
```

### Linting and formatting

Run every now and then:

```bash
cargo fmt
cargo clippy
```

## Design Goals

### Correctness Over Performance

Optimisations can be made once the correctness of the engine has been verified
and validated. A slow engine may be frustrating for the user, but handling
their funds incorrectly is harmful.

### Idempotency

Duplicate transactions are not only not an error, they're expected. Depending
on their source (user entry, network API), retries will happen. Processing a
duplicate transaction should be idempotent.

### Conflicting Transactions

Should the engine receive a transaction ID that conflicts with a previous
transaction of the same ID (e.g. different type, amount, client), the following
approaches were considered and rejected:

1. Fail hard and fast i.e. panic - Doing so would catch the error early, but
   make the engine brittle and open to DOS-style attacks. It would also affect
   user experience: if the credit provider made a mistake handling
   one clients transactions, why should the other clients suffer?
2. Put the previous instance of that transaction ID on hold, and wait for a
   resolution from the credit provider - Doing this assumes that we have some
   mechanism through which to feed back to the provider that such a scenario has
   occurred, and that we're waiting for further input. Similar to option 1, this
   would also be a possible attack surface for preventing clients from accessing
   funds they had previously successfully deposited. Due to the complexity of
   such a function, that is not considered in scope for this engine.
3. Freeze the account associated with the transaction - The difficulty with this
   approach is knowing which account to freeze. What if the two transaction
   instances point to two different clients? Do you freeze both? Could an
   attacker freeze accounts by exploiting this? The potential impact on user
   experience is quite high, and without clarity on requirements this solution
   will be avoided.

For simplicity, the chosen approach is to simply drop the transaction. Ideally,
we'd log the occurrence in an auditable log should we need improvements. This
avoids needing potentially complicated business logic in the engine, and instead
pushes responsibility back onto the credit provider to correct their transaction
data.

### Only Deposits Are Disputable

This handles the case where the credit provider has detected an error or a
fraudulent transfer of funds. Disputing a withdrawal implies there there is some
way our payment engine can receive a chargeback from the provider. To avoid
the complexity of such a situation, we instead limit disputes to incoming
transfers of funds.

### Concurrency

A possible future extension of this engine would be to feed it transactions from
multiple concurrent sources (e.g. multiple large files, TCP sockets). In such
a scenario, a consumer/integrator may wish to use this as a library that is
exercised by multiple async runtime tasks or threads, where each client's
account balance becomes shared state across these contexts.

To keep things simple, this engine is designed not to support concurrency. A
sufficient sprinkling of `Arc` and `Mutex` could be used to change things later
if needs be, but consideration would be needed to minimise the amount of time
any context held a mutex. Possible points:

- Don't mutex the whole engine, only the internal shared state.
- Possible shard the underling data storage.
